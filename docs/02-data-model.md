# Data model

Source of truth: `backend/src/db/migrations/*.sql`. They run in file-name order on boot and are tracked
in `app.schema_migrations`. This page explains them.

All tables live in schema **`app`** (not `public`, which Supabase exposes over REST).
IDs are **UUIDv7** generated by the API: time-ordered, so inserts stay at the right edge of the index.

## Diagram

```
users ──< memberships >── workspaces ──< templates (workspace_id null = built in)
  │            │                │             │
  │            │                ├──< sources ──< source_chunks (vector 384)
  │            │                │
  │            │                ├──< jobs ──< job_inputs
  │            │                │      └──< job_stages
  │            │                │      └── document_id ─┐
  │            │                ├──< documents ◄────────┘
  │            │                │       └──< document_versions
  │            │                └──< audit_events (document_id has no FK on purpose)
  └──< sessions (workspace_id = the one being worked in)
```

## Tables

### users
| Column | Type | Notes |
|---|---|---|
| id | uuid pk | UUIDv7 |
| email | text | unique; stored lowercase (check constraint) |
| name | text | non-empty (check constraint) |
| password_hash | text | `scrypt$N$r$p$salt$hash`; `app_user` has **no** access to this column |
| created_at, updated_at | timestamptz | |

### sessions
One row per sign-in. `token_hash` is SHA-256 of the cookie value; the token itself is never stored.
`workspace_id` is the workspace that session is currently working in (people can belong to several).
Expiry slides forward a day at a time, up to `SESSION_DAYS`.

### workspaces
`plan` is `free | premium | pro` (check constraint). Limits per plan live in `shared/src/catalog.js`,
not in the database, so pricing changes do not need a migration.

### memberships
`(workspace_id, email)` is unique. `user_id` is null while an invitation is pending; the check constraint
`memberships_active_has_user` makes "active with no user" impossible. Roles: `owner | editor | viewer`.

### templates
`id` is text: built-ins keep readable ids (`lecture_notes`), custom ones get `tpl_<uuid>`.
`workspace_id` null means built in, upserted from the shared catalog on every boot.
`fields` is the JSON field schema (the same shape the editor renders and the validator checks).
Deleting a custom template sets `deleted_at`, so documents made from it keep their schema.

### sources and source_chunks
Reference material for the Retrieve stage. `chars` is a generated column. Chunks are ~700 characters,
line-aligned (price lists are line-oriented), each with a `vector(384)` embedding and the `embed_model`
that produced it — vectors from different embedders are never compared.

### jobs, job_inputs, job_stages
One capture = one job = at most one document.

- `jobs.status`: `queued → running → succeeded | failed`. `locked_by`/`locked_at` belong to the worker
  that claimed it; `attempts` bounds retries after a crash.
- `job_inputs`: one row per file, pasted text or link. Exactly one of `storage_key`, `text_content` or
  `source_url` must be set (check constraint). `extracted_text` is filled by the Extract stage.
- `job_stages`: one row per stage, primary key `(job_id, stage)`, with `status`, timestamps and a `log`
  array shown live on the job page.

### documents and document_versions
`content` is JSONB matching the template's field schema. `version` increments on every save, and every
version is kept in `document_versions` (`(document_id, version)` unique).
`search` is a generated `tsvector` over title + content with a GIN index.
Two check constraints keep states honest: `status='approved'` exactly when `approved_at` is set, and
`content` must be a JSON object.

### audit_events
Append-only: `app_user` is granted INSERT and SELECT but **not** UPDATE or DELETE.
`document_id` intentionally has no foreign key, so the trail outlives deleted documents.

## Indexes

Every foreign key is indexed (Postgres does not do it for you, and unindexed FKs make deletes scan).
Beyond those:

| Index | Serves |
|---|---|
| `jobs_queue_idx (created_at) where status='queued'` | the worker's claim query, partial so it stays tiny |
| `jobs_running_idx (locked_at) where status='running'` | stale-job recovery |
| `documents_workspace_updated_idx (workspace_id, updated_at desc)` | the library's default order |
| `documents_search_idx` GIN | full-text search |
| `users_email_key` unique | sign-in |
| `memberships_workspace_email_key` unique | one membership per email per workspace |

## Row-level security

Enabled on every workspace-owned table. Policies target the `app_user` role only:

```sql
create policy documents_workspace_isolation on app.documents to app_user
  using (workspace_id = (select app.current_workspace_id()))
  with check (workspace_id = (select app.current_workspace_id()));
```

`app.current_workspace_id()` reads `current_setting('app.workspace_id')`, which the API sets per
transaction. The `(select …)` wrapper makes Postgres evaluate it once per query instead of once per row.

Templates have their own read policy (`workspace_id is null or workspace_id = current`), so built-ins are
visible to everyone while custom ones stay private.

Proven by tests in `backend/test/documents.test.js` and the direct SQL check in Phase 2:
a workspace cannot read another's rows, and an insert carrying someone else's `workspace_id` is rejected
by the database, not by application code.

## Moving to Supabase

1. Create a project, copy the **pooled** connection string into `DATABASE_URL`.
2. `npm run migrate --workspace backend` — the same migrations create schema `app`, the `app_user` role
   and all policies.
3. Nothing else changes. `pgvector` is available on Supabase; `create extension if not exists vector`
   is already in `001_schema.sql`.

If you would rather use Supabase Auth than our `users`/`sessions` tables, see
[07-handoff.md](07-handoff.md) → "Swapping authentication".
